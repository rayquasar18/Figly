# Phase 07.1: Docker Split - Research

**Researched:** 2026-03-16
**Domain:** Docker multi-container architecture, Next.js standalone, NestJS production deployment
**Confidence:** HIGH

## Summary

Phase 07.1 splits the monolithic `figly-app` Docker container into two independent containers: `figly-frontend` (Next.js standalone on port 3000) and `figly-backend` (NestJS on port 4000). This is a standard Docker Compose multi-service pattern for monorepo applications.

The implementation is already complete. `Dockerfile.frontend` uses a 3-stage build (deps -> build -> runner) producing a minimal Next.js standalone image. `Dockerfile.backend` follows the same 3-stage pattern with Prisma client generation and a `backend-entrypoint.sh` that runs `prisma db push` and `prisma db seed` before starting the NestJS server. The `docker-compose.yml` already defines all 6 services (postgres, redis, minio, minio-init, backend, frontend) with proper dependency ordering and healthchecks.

**Primary recommendation:** The Docker split is already implemented and builds successfully. The plan should validate the existing implementation end-to-end (`docker compose build && docker compose up`) and address any edge-case gaps (environment variable completeness, container-to-container networking, cleanup of the legacy `Dockerfile`).

## Architecture Patterns

### Current Docker Structure
```
Figly/
  Dockerfile              # OLD: Single-container (legacy, to be removed)
  Dockerfile.frontend     # 3-stage: deps -> build -> runner (standalone)
  Dockerfile.backend      # 3-stage: deps -> build -> runner (NestJS dist)
  backend-entrypoint.sh   # Prisma push + seed + node dist/main.js
  docker-compose.yml      # 6 services: postgres, redis, minio, minio-init, backend, frontend
  .dockerignore           # node_modules, .next, dist, .git, .planning, .claude, *.md
```

### Pattern 1: Multi-Stage Docker Build (Frontend)
**What:** 3-stage build for minimal production image with Next.js standalone output
**When to use:** Always for frontend container
**Example:**
```dockerfile
# Stage 1: Install deps with workspace support
FROM node:20-alpine AS deps
COPY frontend/package.json packages/shared/package.json
RUN pnpm install --frozen-lockfile

# Stage 2: Build with turbo (respects dependency graph)
FROM node:20-alpine AS build
ARG NEXT_PUBLIC_API_URL=http://localhost:4000/api
RUN pnpm turbo build --filter=@figly/frontend

# Stage 3: Minimal runner with standalone output
FROM node:20-alpine AS runner
COPY --from=build /app/frontend/.next/standalone ./
COPY --from=build /app/frontend/.next/static ./frontend/.next/static
COPY --from=build /app/frontend/public ./frontend/public
CMD ["node", "frontend/server.js"]
```

### Pattern 2: Multi-Stage Docker Build (Backend)
**What:** 3-stage build for NestJS production with Prisma and entrypoint script
**When to use:** Always for backend container
**Example:**
```dockerfile
# Stage 1: Install deps + copy prisma schema for generate
FROM node:20-alpine AS deps
COPY backend/prisma ./backend/prisma
RUN pnpm install --frozen-lockfile

# Stage 2: Generate Prisma + build
FROM node:20-alpine AS build
RUN cd backend && npx prisma generate
RUN pnpm turbo build --filter=@figly/backend

# Stage 3: Runner with entrypoint for migrate/seed
FROM node:20-alpine AS runner
RUN apk add --no-cache libc6-compat
COPY backend-entrypoint.sh /app/backend-entrypoint.sh
CMD ["/app/backend-entrypoint.sh"]
```

### Pattern 3: Container Networking via Docker Compose
**What:** Services communicate using container names as hostnames within the default Docker network
**When to use:** All inter-container communication
**Key mappings:**
- `postgres` -> `figly-postgres:5432` (DATABASE_URL uses `figly-postgres`)
- `redis` -> `figly-redis:6379` (REDIS_URL uses `figly-redis`)
- `minio` -> `figly-minio:9000` (MINIO_ENDPOINT uses `figly-minio`)
- `backend` -> `figly-backend:4000` (frontend's API_URL uses `localhost:4000` via port mapping)

### Pattern 4: Build-Time vs Runtime Environment Variables
**What:** Next.js `NEXT_PUBLIC_*` vars are inlined at build time, backend vars are runtime
**Critical distinction:**
- Frontend: `NEXT_PUBLIC_API_URL` must be set as `ARG` in Dockerfile and passed via `args:` in docker-compose.yml
- Backend: All env vars (DATABASE_URL, REDIS_URL, etc.) are runtime via `environment:` in docker-compose.yml

### Anti-Patterns to Avoid
- **Single-stage Docker builds:** Bloats final image with devDependencies and build tools
- **Copying node_modules as volume mount:** Breaks reproducibility, creates platform-specific binary issues
- **Hardcoding connection strings:** Use environment variables for all service endpoints
- **Running prisma migrate in Dockerfile build stage:** Migrations require database access; must be in entrypoint at runtime
- **NEXT_PUBLIC_API_URL pointing to container name:** Browser cannot resolve Docker container hostnames; must use host-accessible URL (localhost:4000)

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Database migrations at startup | Custom migration scripts | `prisma db push` in entrypoint.sh | Handles schema diffing, is idempotent |
| Next.js production server | Custom Express wrapper | `output: 'standalone'` + `node frontend/server.js` | Next.js bundles minimal Node server |
| Service dependency ordering | Custom wait scripts | Docker Compose `depends_on` with `condition: service_healthy` | Native Docker health-based ordering |
| MinIO bucket initialization | Manual setup | `minio-init` sidecar service | Runs once, waits for healthy minio |

## Common Pitfalls

### Pitfall 1: NEXT_PUBLIC_API_URL Must Be Build-Time ARG
**What goes wrong:** Frontend builds without the API URL baked in, falls back to localhost which may not work in all deployments
**Why it happens:** NEXT_PUBLIC_ vars are replaced at build time by Next.js, not at runtime
**How to avoid:** Always pass as `ARG` in Dockerfile and `args:` in docker-compose.yml build section
**Warning signs:** API calls fail with network errors when running in Docker

### Pitfall 2: libc6-compat Required for Native Modules on Alpine
**What goes wrong:** `sharp` and `argon2` crash at runtime with missing library errors
**Why it happens:** Alpine uses musl libc instead of glibc; native Node modules compiled against glibc need compatibility layer
**How to avoid:** `RUN apk add --no-cache libc6-compat` in the runner stage of backend Dockerfile
**Warning signs:** `Error: Cannot find module` or `ENOENT` errors for .so files at startup

### Pitfall 3: Prisma Client Must Be Generated Before Build
**What goes wrong:** TypeScript compilation fails with "Cannot find module @prisma/client"
**Why it happens:** Prisma client is generated code, not installed from npm
**How to avoid:** `RUN cd backend && npx prisma generate` BEFORE `pnpm turbo build`
**Warning signs:** Build fails at TypeScript compilation with Prisma-related type errors

### Pitfall 4: Frontend Cannot Use Docker Container Hostnames
**What goes wrong:** Browser-side API calls fail because `http://figly-backend:4000` is not resolvable
**Why it happens:** Browser runs on the host machine, not inside Docker network
**How to avoid:** `NEXT_PUBLIC_API_URL` must be `http://localhost:4000/api` (host-accessible), not container hostname
**Warning signs:** Network errors in browser console, CORS failures

### Pitfall 5: WebSocket CORS in Docker
**What goes wrong:** Socket.IO connections fail with CORS errors
**Why it happens:** Backend FRONTEND_URL must match the origin the browser sends
**How to avoid:** Backend `FRONTEND_URL` env var in docker-compose.yml must be `http://localhost:3000` (what browser sees)
**Warning signs:** WebSocket connection fails, "Access-Control-Allow-Origin" errors

### Pitfall 6: Workspace Package Resolution in Docker
**What goes wrong:** `@figly/shared` package not found during build
**Why it happens:** pnpm workspace requires root `pnpm-workspace.yaml` and all referenced packages
**How to avoid:** Copy `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, and all workspace `package.json` files in deps stage
**Warning signs:** "ERR_PNPM_WORKSPACE_PKG_NOT_FOUND" during install

### Pitfall 7: Legacy Dockerfile Confusion
**What goes wrong:** Running `docker build .` uses the old single-container `Dockerfile` instead of the split ones
**Why it happens:** Default `Dockerfile` still exists in the project root
**How to avoid:** Remove or rename the legacy `Dockerfile`, always use `docker compose build`
**Warning signs:** Single container trying to run both frontend and backend
