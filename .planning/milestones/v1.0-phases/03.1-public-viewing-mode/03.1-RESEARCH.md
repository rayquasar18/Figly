# Phase 3.1: Public Viewing Mode - Research

**Researched:** 2026-03-14
**Domain:** Authentication architecture refactoring, public route patterns, frontend auth gating
**Confidence:** HIGH

## Summary

Phase 3.1 requires enabling non-authenticated users to view public content (profiles, posts, feeds) in read-only mode. Currently, ALL app routes in both backend and frontend are gated behind authentication -- the backend uses `@UseGuards(JwtAuthGuard)` at the controller level on every non-auth endpoint, and the frontend `(app)/layout.tsx` redirects unauthenticated users to `/login` before rendering any content.

The changes span three layers: (1) Backend -- creating an `OptionalJwtAuthGuard` that enriches the request with user info when a valid JWT cookie is present but allows the request through without error when no token exists, plus refactoring service methods that currently require `viewerId` to accept `viewerId | null`; (2) Frontend routing -- introducing a new `(public)` route group that does NOT gate on authentication, while keeping the existing `(app)` group for authenticated-only pages; (3) Frontend UI -- conditionally showing/hiding interactive elements (like, bookmark, comment, follow buttons) based on auth state, with CTAs redirecting to login.

**Primary recommendation:** Create an `OptionalJwtAuthGuard` by extending the existing `JwtAuthGuard` to catch auth errors and set `req.user = null`, then create new public-facing API endpoints (or refactor existing ones) that use this guard. Frontend uses a new `(public)` route group with its own layout that does not redirect to login.

## Architecture Patterns

### Pattern 1: OptionalJwtAuthGuard (Backend)

**What:** A guard that attempts JWT authentication but allows the request through even if no token is present. When a valid token exists, `req.user` is populated. When no token exists, `req.user` is set to `null`.

**When to use:** Any endpoint that should return data to both authenticated and unauthenticated users, but enriches the response when authenticated (e.g., `isLiked`, `isFollowing`).

**Implementation:**

```typescript
// backend/src/auth/guards/optional-jwt-auth.guard.ts
import { Injectable, ExecutionContext } from '@nestjs/common';
import { AuthGuard } from '@nestjs/passport';

@Injectable()
export class OptionalJwtAuthGuard extends AuthGuard('jwt') {
  canActivate(context: ExecutionContext) {
    // Call parent canActivate to attempt JWT validation
    return super.canActivate(context);
  }

  handleRequest(err: any, user: any, info: any) {
    // If no token or invalid token, don't throw -- just return null
    // This allows the request through without a user
    if (err || !user) {
      return null;
    }
    return user;
  }
}
```

**Why this works:** The `handleRequest` method is the Passport integration point. Normally `AuthGuard('jwt')` throws `UnauthorizedException` when auth fails. By overriding `handleRequest`, we swallow the error and return `null` instead, meaning `req.user` will be `null` for unauthenticated requests but populated for authenticated ones.

**Confidence:** HIGH -- this is the standard NestJS pattern for optional authentication documented in NestJS official recipes.

### Pattern 2: Service Methods Accept Optional viewerId

**What:** Refactor service methods like `getPost(postId, viewerId)` to accept `viewerId: string | null`. When `viewerId` is `null`, skip the like/bookmark/follow status lookups and return `isLiked: false`, `isBookmarked: false`, `isFollowing: false`.

**Example:**

```typescript
// In PostsService
async getPost(postId: string, viewerId: string | null) {
  const post = await this.prisma.post.findUnique({ /* existing query */ });

  if (!post) throw new NotFoundException('...');

  // Only check interaction status if viewer is authenticated
  let isLiked = false;
  let isBookmarked = false;

  if (viewerId) {
    const [likes, bookmarks] = await Promise.all([
      this.prisma.like.findMany({ where: { userId: viewerId, postId: { in: [postId] } } }),
      this.prisma.bookmark.findMany({ where: { userId: viewerId, postId: { in: [postId] } } }),
    ]);
    isLiked = likes.some(l => l.postId === postId);
    isBookmarked = bookmarks.some(b => b.postId === postId);
  }

  return { ...postData, isLiked, isBookmarked };
}
```

**Confidence:** HIGH -- straightforward null-check pattern.

### Pattern 3: Frontend Public Route Group

**What:** Create a new `(public)` route group in Next.js App Router alongside the existing `(app)` and `(auth)` groups. The `(public)` layout does NOT redirect to login -- it optionally checks auth state to enrich the UI but renders content regardless.

**Current route structure:**
```
src/app/
  (app)/          # Requires auth - redirects to /login
    layout.tsx    # Auth gate: redirects if !user
    page.tsx      # Feed (personal)
    [username]/   # Profile
    post/[postId] # Post detail
    saved/        # Saved posts
  (auth)/         # Auth pages - redirects if user exists
    layout.tsx
    login/
    signup/
```

**Proposed route structure:**
```
src/app/
  (app)/          # Authenticated-only routes
    layout.tsx    # Auth gate preserved
    page.tsx      # Personal feed
    saved/        # Saved posts (auth-only)
    complete-profile/
  (public)/       # Public-accessible routes (optional auth)
    layout.tsx    # Does NOT redirect to login; shows optional auth banner
    [username]/   # Profile page (public)
    post/[postId] # Post detail (public)
    feed/         # Public discovery feed
  (auth)/         # Auth pages
    layout.tsx
    login/
    signup/
```

**Key insight:** Both `(app)/[username]` and `(public)/[username]` would resolve to `/:username` which creates a conflict. The solution is to MOVE the profile and post routes OUT of `(app)` and INTO `(public)`, since these pages need to work for both authenticated and unauthenticated users. The `(public)` layout checks auth optionally and renders different UI (full nav vs minimal nav with login CTA).

**Revised approach -- single shared layout for dual-access pages:**

```
src/app/
  (app)/              # Auth-only routes
    layout.tsx        # Strict auth gate
    page.tsx          # Personal feed
    saved/
    complete-profile/
  (public)/           # Public-accessible (optional auth)
    layout.tsx        # Optional auth check, no redirect
    [username]/       # Profile (works auth + unauth)
    post/[postId]/    # Post detail (works auth + unauth)
    explore/          # Public feed / discovery
  (auth)/             # Login/signup pages
    layout.tsx
    login/
    signup/
```

**Confidence:** HIGH -- Next.js route groups are designed for this pattern.

### Pattern 4: Frontend Auth-Aware Components

**What:** Components like `PostActions`, `CommentInput`, `FollowButton` check auth state and either render interactively (when authenticated) or render as disabled/hidden (when not).

**Two approaches:**

1. **Hide interactive elements entirely** for unauthenticated users and show a login CTA banner
2. **Show elements in disabled state** that redirect to login on click

**Recommended: Approach 2** -- showing buttons that redirect to login is better for engagement because:
- Users can see what they're missing (FOMO)
- Clear call-to-action to sign up
- Better conversion than just hiding features

**Implementation:**

```typescript
// Utility hook
export function useIsAuthenticated(): boolean {
  const user = useAuthStore((s) => s.user);
  return !!user;
}

// In PostActions component
const isAuthenticated = useIsAuthenticated();
const router = useRouter();

const handleLikeToggle = () => {
  if (!isAuthenticated) {
    router.push('/login');
    return;
  }
  // existing toggle logic
};
```

**Confidence:** HIGH -- standard social media pattern.

### Pattern 5: Public Feed Endpoint

**What:** The existing `/feed` endpoint is user-specific (shows posts from followed users). For unauthenticated users, create a `/feed/public` endpoint that returns recent posts globally (chronological, latest first).

**Why not reuse /feed:** The existing feed requires userId to filter by followed users. A public feed serves a fundamentally different purpose -- discovery of content to encourage signup.

**Confidence:** HIGH -- simple new endpoint.

### Anti-Patterns to Avoid

- **Making JwtAuthGuard globally optional:** Do NOT change the existing `JwtAuthGuard` behavior. Create a NEW guard (`OptionalJwtAuthGuard`). Modifying the existing guard could break auth requirements on protected routes.
- **Duplicating controllers for public vs private:** Do NOT create separate `PublicPostsController` and `PostsController`. Instead, use `OptionalJwtAuthGuard` on read endpoints and keep `JwtAuthGuard` on write endpoints within the same controller.
- **Removing auth from write endpoints:** Only read endpoints (GET) should use optional auth. All write endpoints (POST, PATCH, DELETE) MUST remain behind `JwtAuthGuard`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Optional JWT validation | Custom token parsing/verification | Passport's `handleRequest` override | Passport already handles cookie extraction, token verification, expiry |
| Route group auth gating | Custom middleware for public vs private | Next.js route groups + layout auth checks | Built-in App Router pattern, zero config |
| Auth state in components | Prop drilling isAuthenticated | Zustand useAuthStore | Already exists, global singleton |

## Common Pitfalls

### Pitfall 1: Route Conflicts Between (app) and (public)

**What goes wrong:** If both `(app)/[username]` and `(public)/[username]` exist, Next.js will throw a build error because both resolve to `/:username`.
**Why it happens:** Route groups are transparent in URL -- they only affect layout, not URL path.
**How to avoid:** Move `[username]` and `post/[postId]` to ONLY live under `(public)`. The `(public)` layout uses optional auth -- if user is authenticated, they see full UI. If not, they see read-only.
**Warning signs:** Build error: "Conflicting routes found at /:username."

### Pitfall 2: API Client 401 Interceptor Redirecting to Login

**What goes wrong:** The current `api-client.ts` interceptor catches 401 errors and redirects to `/login`. For public routes, a 401 should NOT cause a redirect -- it should just mean the user isn't authenticated.
**Why it happens:** The interceptor was designed assuming all API calls are authenticated.
**How to avoid:** Public-facing API calls should go to endpoints with `OptionalJwtAuthGuard` which never return 401 (they return 200 with null user context). Alternatively, the interceptor should check the current route before redirecting.
**Warning signs:** Viewing a public profile suddenly redirects to login.

### Pitfall 3: useMe Query Firing on Public Pages

**What goes wrong:** The `useMe()` hook fires on every page load. On public pages, if there's no cookie, it returns 401, which triggers the 401 interceptor and redirects to login.
**Why it happens:** `useMe()` is called in the `(app)` layout, and if also called on public pages, will attempt auth.
**How to avoid:** In the `(public)` layout, call `useMe()` but configure it with `retry: false` and handle the error case by setting user to null (not redirecting). The existing hook already has `retry: false`, which is good. The key fix is the interceptor -- it should NOT redirect for the `/auth/me` endpoint 401 failure when on a public page.
**Warning signs:** Flash of login page when visiting public profile directly.

### Pitfall 4: Presigned URLs Needing Auth

**What goes wrong:** Media URLs are presigned S3 URLs generated by the backend. These URLs are self-authenticating (contain signature in query params), so they work for anyone with the URL. This is NOT a problem -- just verify this is the case.
**Why it matters:** If the backend were serving media through an authenticated endpoint instead, public users couldn't see images.
**How to avoid:** Current implementation uses S3 presigned URLs via `StorageService.getPresignedUrl()` -- these are inherently public for the TTL period. No changes needed for media access.
**Warning signs:** Broken images on public pages.

### Pitfall 5: Forgetting to Handle null viewerId in Service Layer

**What goes wrong:** If `req.user` is null (unauthenticated) but the controller passes `req.user.userId` without null-checking, it throws a runtime error.
**Why it happens:** All current controllers destructure `const { userId } = req.user as any;` without null checks.
**How to avoid:** For endpoints using `OptionalJwtAuthGuard`, extract viewerId safely: `const viewerId = (req.user as any)?.userId || null;`
**Warning signs:** 500 errors when unauthenticated users hit public endpoints.

## Code Examples

### OptionalJwtAuthGuard

```typescript

import { Injectable, ExecutionContext } from '@nestjs/common';
import { AuthGuard } from '@nestjs/passport';

@Injectable()
export class OptionalJwtAuthGuard extends AuthGuard('jwt') {
  canActivate(context: ExecutionContext) {
    return super.canActivate(context);
  }

  handleRequest(err: any, user: any) {
    // Don't throw on auth failure -- just return null
    return user || null;
  }
}
```

### Refactored PostsController (Read Endpoints)

```typescript
@Controller('posts')
export class PostsController {
  // READ endpoints: optional auth
  @Get('user/:username')
  @UseGuards(OptionalJwtAuthGuard)
  async getUserPosts(
    @Param('username') username: string,
    @Req() req: Request,
    @Query('cursor') cursor?: string,
  ) {
    const viewerId = (req.user as any)?.userId || null;
    return this.postsService.getUserPosts(username, viewerId, cursor);
  }

  @Get(':id')
  @UseGuards(OptionalJwtAuthGuard)
  async getPost(@Param('id') postId: string, @Req() req: Request) {
    const viewerId = (req.user as any)?.userId || null;
    return this.postsService.getPost(postId, viewerId);
  }

  // WRITE endpoints: strict auth
  @Post()
  @UseGuards(JwtAuthGuard, EmailVerifiedGuard)
  async createPost(@Body() dto: CreatePostDto, @Req() req: Request) {
    const { userId } = req.user as any;
    return this.postsService.createPost(userId, dto);
  }
  // ... like, bookmark, delete remain JwtAuthGuard
}
```

## API Client Interceptor Fix

The current `api-client.ts` interceptor redirects to `/login` on 401 refresh failure. This must be modified to only redirect when the user is on an authenticated route. For public routes, 401 should be silently swallowed.

```typescript
// Modified interceptor catch block
} catch (refreshError) {
  processQueue(refreshError as AxiosError);
  // Only redirect if on an auth-required route
  if (typeof window !== 'undefined') {
    const publicPaths = ['/post/', '/explore', '/discover'];
    const isPublicPage = publicPaths.some(p => window.location.pathname.includes(p))
      || /^\/[^/]+$/.test(window.location.pathname); // username routes

    if (!isPublicPage) {
      window.location.href = '/login';
    }
  }
  return Promise.reject(refreshError);
}
```

**Better approach:** Since public endpoints use `OptionalJwtAuthGuard` and never return 401, the interceptor issue only applies to the `/auth/me` call. The fix is simpler -- the `useMe` hook already has `retry: false`, and the `(public)` layout should handle `useMe` error by setting user to null rather than redirecting.

## Open Questions

1. **Should followers/following lists be publicly accessible?**
   - What we know: Currently gated behind JwtAuthGuard in SocialController
   - What's unclear: Whether showing follower/following counts is enough for public profiles, or if the actual lists should be browsable
   - Recommendation: Make followers/following lists public for now (read-only). This aligns with Instagram's model. Can restrict later if needed.

2. **Should the public discovery feed show all posts or curated content?**
   - What we know: No algorithmic feed exists yet (SOCL-V2-01 is v2)
   - What's unclear: Whether showing all recent posts is too noisy or if it encourages signup
   - Recommendation: Simple chronological feed of recent posts (latest 50). This is a MVP approach. Pagination included.

3. **Open Graph / SEO meta tags for social sharing**
   - What we know: All current pages are client-rendered (`'use client'`). Next.js can generate static metadata for server components.
   - What's unclear: Whether client-side rendering is sufficient for social sharing previews (Facebook, Twitter crawlers need SSR meta tags)
   - Recommendation: For this phase, focus on making content accessible. OG tags can be a follow-up enhancement. The `(public)` route pages can potentially use server components for metadata generation while rendering client components for the interactive content. This is a stretch goal, not a blocker.
