6. **Fix API client interceptor** in `frontend/src/lib/api-client.ts`:
   - In the 401 refresh failure catch block, do NOT redirect to /login when on a public page
   - Detect public pages by checking `window.location.pathname`:
     - Public paths: any path matching `/explore`, or paths starting with `/post/`, or single-segment paths that could be usernames (matches `^/[^/]+$` but NOT `/login`, `/signup`, `/saved`, `/complete-profile`)
   - Simpler approach: check if the 401 came from the `/auth/me` endpoint specifically. If so, do NOT redirect -- the public layout handles this gracefully. Only redirect for other 401s that occur on non-public routes.
   - Best approach from research: Only redirect when NOT on a public page. Use a list of auth-required path prefixes: `['/', '/saved', '/complete-profile']` where exact match on `/` means the personal feed. For all other paths, swallow the redirect and let the layout handle it.
   - IMPORTANT: The simplest correct fix -- the `/auth/me` endpoint never causes redirect issues because `useMe()` already has `retry: false` and the (public) layout handles the error. The real issue is: if any API call from a public page hits 401 and triggers the interceptor. Since public endpoints now use OptionalJwtAuthGuard (never return 401), the only 401 that can fire on public pages is from `/auth/me`. So: in the catch block for refresh failure, add a check: `const isAuthCheck = originalRequest.url?.includes('/auth/me'); if (!isAuthCheck) { window.location.href = '/login'; }`. This skips redirect only for the /auth/me 401, which the layout handles.
